Continuum

A management console for organisations migrating from Group Policy to Intune.

Use ← → arrow keys to navigate

The problem — 1 of 3

Intune has no undo.

Group Policy admins have decades of tooling: backup, version history, change tracking. Intune has effectively none of it.

If someone edits a policy badly, or deletes one, there is no version history to restore from and no record of what it used to say. The tenant simply reflects the new state as though it had always been that way.
The problem — 2 of 3

Co-managed devices lie about what's enforced.

Group Policy Looks correctly configured

Every GPO tool the admin has — GPResult, RSoP, the console itself — shows the setting applied. No error. No warning.

Intune MDM Silently wins

When a device gets policy from both worlds, MDM overrides Group Policy. The GPO simply stops taking effect.

An admin believes a security setting is enforced on 500 machines. On the co-managed ones, it isn't.
The problem — 3 of 3

Nobody can answer: are we ready to migrate?

Migration decisions get made on intuition, because the data to make them properly is scattered across per-device diagnostics nobody has time to collect, read, and correlate.

What Continuum is

One console. Three questions.

QuestionAnswered by
What did this policy look like before someone changed it? Policy history + restore
Where is Intune silently overriding Group Policy? Conflict validation across the fleet
Is this fleet ready to migrate? The two above, joined per device

The third is the point. Policy drift and MDM/GPO conflict are far more useful side by side than apart — no existing tool puts them together. That combination is the product.

What exists today

Not a prototype.

~8,100 lines of PowerShell, working, in real production use.
Policy Backup — 5 scripts

Snapshots every Settings Catalog policy to JSON and a versioned Excel workbook, loads history into a single-file SQLite database, and restores from any snapshot — create-only, never overwrites. Change detection hashes settings and assignments, not display names.

MDM/GPO Conflict Validation — 3 scripts

Collects evidence from a device and builds a self-contained interactive HTML report; generates a GPO→CSP mapping catalogue from local ADMX files, no internet required; runs the collector across a fleet from a management server.

Differentiator — 1 of 3

Evidence, not inference.

Evidence What Windows itself states

The "Blocked Group Policies" table, parsed straight from MdmDiagnosticsTool.exe. Authoritative — Windows' own record of what MDM overrode.

Inference What the tool guessed

Name-similarity matching between GPO and CSP settings. Labelled as a guess and given a confidence tier — never presented as fact.

Most tools present one confidence level for everything. In an audit or an incident review, that difference matters enormously.

Differentiator — 2 of 3

Four states, not three.

CodeStateMeaning
0 Clean Checked — nothing found.
1 Fatal The run did not complete.
2 Conflicts found Actionable — not a failure.
3 Degraded Ran, but evidence was incomplete. A 0 elsewhere in this run is not conclusive.

State 3 is the one that matters: instead of a reassuring green zero, the tool says "I couldn't tell." That distinction survives into the UI as a first-class state — it is never flattened.

Differentiator — 3 of 3

It doesn't need the keys.

  • No agent to install on managed devices.
  • No cloud service — runs on your management server, on your network.
  • No credential delegation. Fleet runs use a Copy delivery mode that sidesteps the PowerShell double-hop problem entirely.
  • Report-only by default. It never auto-modifies tenant policy; restore is create-only.
  • Works offline. Mapping generation uses local ADMX files and the registry; reports are self-contained HTML with no CDN calls.
For a security-sensitive buyer, this list is the sales pitch.

Expansion

Where it grows next.

Near-term, high value
  • Deletion detection — flag anything that vanished since the last run.
  • Scheduled, unattended operation — cert-based auth, drift alerting.
  • Snapshot diff — settings and assignments, version to version.
  • Capture what's dropped today — scope tags, template references.
Medium-term
  • More policy types — beyond Settings Catalog.
  • Migration recommendations — the GPO→CSP catalogue, turned into guidance.
  • Compliance mapping — CIS/NIST benchmark alignment.
Longer-term
  • Multi-tenant / MSP mode — one console, many customer tenants.
  • Hosted offering — deliberately out of scope for now; local-only is a feature.
What it does not do

Honesty, by design.

Every one of these is a known, deliberate boundary rather than an oversight. Volunteering them is what makes the rest credible.

  • Settings Catalog only. Other Intune policy types aren't backed up yet.
  • Secrets don't round-trip. Graph never returns secret-typed values on read — a restored policy's password or certificate field will be blank, and the tool says so.
  • Restore doesn't reassign. It recreates the policy and prints the original assignments for a human to reapply — deliberately, not automatically.
  • GPO→CSP matching is heuristic. Name similarity, not a Microsoft-published mapping — on a real device the highest-confidence tier produced 0 matches out of 3,549 ADMX policies.
  • "Last modified by" is best-effort, limited to the tenant's audit retention window.
  • Single administrator, no accounts in the first release. Multi-user is Phase 5.
Who it's for

And why they buy.

Primary

IT admins and infra teams running a hybrid Windows estate mid-migration, at a scale where per-device diagnostics no longer work.

Secondary

MSPs running migrations for clients, who need evidence and reporting they can hand over. Multi-tenant support unlocks this properly.

Tertiary

Security and compliance owners who need to demonstrate a policy was enforced — and evidence of when it wasn't.

This finds them, proves it with Windows' own evidence, and tracks every policy change so you can see what moved and put it back.”
